## 1. 状態定義（何を持てば探索できるか）

* **入力（固定情報）**

  * `top[4]`：各列を上から見た見える数（col1top〜col4top）
  * `bottom[4]`：各列を下から見た見える数（col1bottom〜col4bottom）
  * `left[4]`：各行を左から見た見える数（row1left〜row4left）
  * `right[4]`：各行を右から見た見える数（row1right〜row4right）

* **盤面（探索対象）**

  * `grid[4][4]`：各マスの高さ（1〜4）。未確定は 0 などで表す。

* **制約管理（高速な重複チェック用）**

  * `row_used[4]`：各行で使われた数字集合（1〜4）
  * `col_used[4]`：各列で使われた数字集合（1〜4）
  * 実装では「集合」を **ビットマスク**（例：1〜4を4bit）で持つと速い

    * 目的：候補生成を O(1) に近づける（「その数字はもう行/列にある？」）

* **探索の進捗（どこまで決めたか）**

  * 代表案は2つ（どちらでもOK、4x4なら両方現実的）

    * A案：`pos`（0..15）でセルを1個ずつ埋める
    * B案：`r`（0..3）で **行ごとに確定**していく（おすすめ：枝刈りが強く、実装も読みやすい）
  * この問題は「各行・各列が 1..4 を1回ずつ含む（Latin）」＋「見える数（Skyscrapers）」なので、**行を“順列”として確定**させる方針が非常に相性が良い

* **候補集合（前処理すると強い）**

  * `row_candidates[r]`：行 r に入りうる **長さ4の順列**の一覧（最大24個）

    * 条件：その順列の `visible_from_left == left[r]` かつ `visible_from_right == right[r]`
  * これを作っておくと、探索は

    * 「行 r に候補順列を1つ選ぶ」→「列重複がないか」→「列の見える数が成立しうるか」
    * という流れにでき、分岐数が激減します（24^4 ではなく、もっと小さくなる）

## 2. 関数分割（指定フォーマット）

### 入力・検証

* **関数名:** `parse_clues`

* **目的（責務）:**

  * コマンドライン引数の文字列を分解し、`top/bottom/left/right` の4配列に格納
  * 文字が '1'〜'4' か、要素数が16個か、スペース区切りの形式かを検証

* **引数:**

  * 引数文字列（例：`"3 2 1 2 2 2 3 1 2 2 1 3 2 2 3 1"` 相当）
  * 出力先配列 `top[4], bottom[4], left[4], right[4]`

* **戻り値:**

  * 成功/失敗（真偽）

* **関数名:** `basic_clue_sanity_check`

* **目的（責務）:**

  * 明らかに矛盾するヒントを弾く（探索前の軽い不可能判定）
  * 例：見える数は必ず1〜4
  * 例：見える数が4なら並びは必ず 1,2,3,4（単調増加）などの“強制”を使って矛盾検出

* **引数:**

  * `top/bottom/left/right`

* **戻り値:**

  * 真偽

---

### 見える数（Skyscraper）計算・部分チェック

* **関数名:** `visible_count`

* **目的（責務）:**

  * 長さ4の配列（または確定済み行/列）について、端から見える箱の数を計算

* **引数:**

  * 長さ4の列 `a[4]`
  * 方向（左→右 / 右→左 などは呼び出し側で反転して渡してもよい）

* **戻り値:**

  * 見える数（1〜4）

* **関数名:** `visible_partial_feasible`

* **目的（責務）:**

  * **途中まで埋まった列/行**が、最終的に指定の見える数になりうるかを判定（枝刈り）
  * 例：列の上から見える数 `top[c]` に対して、

    * すでに見えている数が `top[c]` を超えたら即アウト
    * 残りの未確定マスにどんな数字を置いても `top[c]` に到達できないならアウト

* **引数:**

  * 途中状態の列（確定値＋未確定）
  * その列の使用済み集合 `col_used[c]`（残り候補の推定に使う）
  * 目標 `target`（top or bottom）
  * 方向（上から/下から）

* **戻り値:**

  * 真偽

> 部分可否判定は「厳密最適」までやらなくてもOK。4x4なら
>
> * **下限（既に見えている数）**
> * **上限（残りで最大どこまで見えるかの楽観見積もり）**
>   の範囲で `target` が入るかを見るだけでも枝刈り効果が出ます。

---

### 行候補（順列）生成

* **関数名:** `generate_all_perms_1to4`

* **目的（責務）:**

  * {1,2,3,4} の順列をすべて生成（24個）
  * 生成手法は何でもよい（次順列・再帰生成など）。ここは一度作れば固定。

* **引数:**

  * 出力先 `perms[24][4]` のような領域

* **戻り値:**

  * 生成個数（24）

* **関数名:** `filter_row_candidates`

* **目的（責務）:**

  * 全順列から、行 r の `left[r]` と `right[r]` を満たすものだけを抽出

* **引数:**

  * `perms`
  * `left[r], right[r]`
  * 出力先 `row_candidates[r]`（候補リスト）

* **戻り値:**

  * 候補数

---

### バックトラッキング本体（行ごと確定方針：おすすめ）

* **関数名:** `solve_by_rows`

* **目的（責務）:**

  * 行 r を上から順に（または選び方を工夫して）候補順列から選んで盤面を埋める
  * 「最初に見つかった解で停止」する

* **引数:**

  * `r`（次に埋める行番号）
  * `grid`
  * `row_candidates`
  * `col_used`
  * `top/bottom/left/right`

* **戻り値:**

  * 解が見つかったか（真偽）
  * ※見つかった場合、`grid` は解で埋まっている状態にする（呼び出し側がそのまま出力）

* **関数名:** `can_place_row`

* **目的（責務）:**

  * 行 r に候補順列 `cand[4]` を置けるか判定（枝刈りの中核）
  * チェック内容（箇条書きの通り実装するイメージ）

    * 各列 c で `cand[c]` が `col_used[c]` に含まれていない（列の重複禁止）
    * 置いた結果、各列について `top/bottom` の **部分可否**が成立（`visible_partial_feasible`）

* **引数:**

  * 行番号 r
  * 候補 `cand[4]`
  * 現在の `col_used`
  * `grid`（列の部分状態を見るなら必要）
  * `top/bottom`

* **戻り値:**

  * 真偽

* **関数名:** `apply_row` / `undo_row`

* **目的（責務）:**

  * `apply_row`：行 r に `cand` を反映（grid更新＋col_used更新）
  * `undo_row`：元に戻す（バックトラック）

* **引数:**

  * 行番号 r
  * 候補 `cand[4]`
  * `grid`, `col_used`

* **戻り値:**

  * なし

* **関数名:** `final_check_all_cols`

* **目的（責務）:**

  * 全行が埋まった時点で、各列の `top/bottom` が完全一致するかを最終確認
  * （部分チェックを入れていても最終確認は必須）

* **引数:**

  * `grid`
  * `top/bottom`

* **戻り値:**

  * 真偽

* **関数名:** `print_grid`

* **目的（責務）:**

  * 解のフォーマットで出力（rush01の仕様に合わせる）

* **引数:**

  * `grid`

* **戻り値:**

  * なし

---

### 探索方針（行ごと確定）の要点まとめ

* **深さ r（0..3）＝「どの行まで確定したか」**
* 分岐＝「その行に入れる順列候補のどれを選ぶか」
* 枝刈り＝

  * 列の重複禁止（即死）
  * 列の見える数 `top/bottom` の **部分可否判定**（早期に不可能を除外）
* 終了条件＝

  * r==4（全行確定）→列の最終チェック→真なら即 return（最初の解で終了）

## 3. 手作業ログ（小さい入力例で10〜20ステップ）

ここでは「解が1つは確実にある」具体例で、**行ごと確定方式**のログを見せます。
（入力例：16個のヒント）

* `top`    : 3 2 1 2
* `bottom` : 2 2 3 1
* `left`   : 2 2 1 3
* `right`  : 2 2 3 1

（このヒントで成立する解の一例は、後でログの中に自然に出てきます）

---

### 事前準備（候補生成のイメージ）

* 全順列（24個）から、各行 r について

  * `visible(left)==left[r]` かつ `visible(right)==right[r]`
  * を満たす順列だけを `row_candidates[r]` に残す

例）

* row3（0-indexで r=2）のヒントは `left=1, right=3`

  * `left=1` になるのは **先頭が4** の順列だけ（4が全部隠すから）
  * そこから `right=3` になるものだけ残る（候補がかなり減る）

---

### 探索ログ（15ステップ）

> 表記：
>
> * 行 r に候補 `cand` を試す
> * 列重複OK?
> * 列の top/bottom 部分可否OK?
> * OKなら確定して次の行へ、NGなら戻って次候補へ

1. **Start**：r=0、列使用は全部空、gridは空

2. r=0 の候補リストから先頭候補を試す

   * 例：cand = [2,1,4,3]（left=2, right=2 を満たす候補の一つ）
   * 列重複：全列未使用なのでOK
   * 列部分可否：

     * col3 は先頭に 4 が立つので top は将来 1 になりやすい（ただし目標 top[2]=1 なので好都合）
     * 他列も「見えている数が目標を超えていない」のでOK
   * **apply**：row0確定、col_used 更新

3. r=1 に進む。候補（left=2, right=2）から試す

   * 例：cand = [3,4,1,2]
   * 列重複チェック：

     * col0：既に 2 があるが 3 は未使用 → OK
     * col1：既に 1 があるが 4 は未使用 → OK
     * col2：既に 4 があるが 1 は未使用 → OK
     * col3：既に 3 があるが 2 は未使用 → OK
   * 列部分可否（top/bottom）：

     * col2 は [4,1,*,*] となり、上からの可視数はもう「1」（4だけ）で固定に近い → top[2]=1 と整合
     * 他列も「既に見えすぎていない」のでOK
   * **apply**：row1確定

4. r=2（left=1, right=3）へ

   * left=1 より、先頭が4の候補だけに絞られる（候補数が激減）

5. r=2 の候補を1つ試す

   * 例：cand = [4,2,3,1]
   * 列重複：

     * col0：既に [2,3] がある、4は未使用 → OK
     * col1：既に [1,4] がある、2は未使用 → OK
     * col2：既に [4,1] がある、3は未使用 → OK
     * col3：既に [3,2] がある、1は未使用 → OK
   * 列部分可否：

     * col0 は [2,3,4,_] で上からの可視がすでに 3（2→3→4）になっている → top[0]=3 と一致方向でOK
     * col3 は [3,2,1,_] で上からの可視は 1（3だけ見える）だが、残りに 4 が来れば2になる → top[3]=2 に到達可能でOK
   * **apply**：row2確定

6. r=3（left=3, right=1）へ

   * right=1 なので **末尾が4** の候補だけに絞られる
   * left=3 も同時に満たす必要がある

7. r=3 の候補を試す

   * 例：cand = [1,3,2,4]（left=3, right=1 の代表格）
   * 列重複：

     * col0：既に [2,3,4] があるので残りは1しかない → candは1で一致、OK
     * col1：既に [1,4,2] があるので残りは3 → candは3でOK
     * col2：既に [4,1,3] があるので残りは2 → candは2でOK
     * col3：既に [3,2,1] があるので残りは4 → candは4でOK
   * ここで **列は全部 1..4 が揃うことが確定**（重複チェックだけで強制される）

8. **apply**：row3確定、r==4（全行完了）

9. 最終列チェック `final_check_all_cols`

   * col0 = [2,3,4,1]

     * top: 2→3→4 で 3、bottom: 1→4 で 2 → (top=3, bottom=2) OK
   * col1 = [1,4,2,3]

     * top: 1→4 で 2、bottom: 3→（4が見える）で 2 → OK
   * col2 = [4,1,3,2]

     * top: 4だけで 1、bottom: 2→3→4 で 3 → OK
   * col3 = [3,2,1,4]

     * top: 3→4 で 2、bottom: 4だけで 1 → OK

10. **解が見つかったので即終了**（「最初に見つかった解のみ」）

11. `print_grid`：4行を出力（rush01形式）

12〜15.（もしここまでに不一致が出ていたら）

* r=3 の別候補へ、なければ r=2 に戻る…という形で探索が続く
* しかしこの例では最初の流れで当たりを引いた、というログ

---

# 自分が実装するときのチェックリスト（必須）

* [ ] 入力文字列を **16個の '1'〜'4'** として正しくパースできている（順序：top→bottom→left→right）
* [ ] `row_candidates[r]` が **left/right と一致する順列だけ**になっている
* [ ] 探索の深さが「行 r を決める」になっている（方針がブレていない）
* [ ] `can_place_row` で最低限これを見ている

  * [ ] 列の重複禁止（`col_used`）
  * [ ] 列の top/bottom の **部分可否**（超過や到達不能の早期枝刈り）
* [ ] `apply_row` で更新したものを `undo_row` で **完全に元に戻す**（col_used と grid）
* [ ] 全行確定時に `final_check_all_cols` を必ず通す（部分チェックの漏れ対策）
* [ ] 「最初の解で打ち切り」になっている（solveが true を返したら上位も即 return）
* [ ] 出力フォーマット（スペース・改行）が rush01 の要求と一致している
* [ ] デバッグ時は

  * [ ] r、試した候補、弾かれた理由（列重複 or 可視不可能）を追えるログ点を用意している

必要なら、あなたが想定している **探索方針（セル埋め/行確定）**がどちらかに合わせて、`visible_partial_feasible` の作り方（下限/上限の見積もり）を、もう一段だけ具体的に“式と考え方”で整理します。
